### 第二十六章：并发：介绍

> 操作系统的并发（Concurrency）主要是由多任务执行的需求以及操作系统提供的进程、线程和调度机制带来的。

**进程（Process）**是操作系统进行资源分配和隔离的基本单位，而**线程（Thread）**是操作系统进行 CPU 调度的基本单位。

最核心的区别在于：进程拥有相对独立的虚拟地址空间和系统资源，而同一个进程中的多个线程共享进程的资源，但各自拥有独立的执行上下文。

**共享资源存在的依据：因为同一个进程中的多个线程共享进程的虚拟****地址空间****。**

#### 具体情景

```C++
#include <stdio.h>
#include <pthread.h>

static volatile int counter = 0;

void *mythread(void *arg) {
    printf("%s: begin\n", (char *)arg);
    int i;
    for (i = 0; i < 1e7; i++) {
        counter = counter + 1;
    }
    printf("%s: done\n", (char *)arg);
    return NULL;
}

int main(int argc, char *argv[]) {
    pthread_t p1, p2;
    printf("main: begin (counter = %d)\n", counter);

    pthread_create(&p1, NULL, mythread, "A");
    pthread_create(&p2, NULL, mythread, "B");

    pthread_join(p1, NULL);
    pthread_join(p2, NULL);

    printf("main: done with both (counter = %d)\n", counter);
    return 0;
}
```

最终代码的执行结果令人震惊，最终的 `counter` 不一定等于 20000000。不仅结构不符合预期，并且每次的输出都不一致。为什么会出现这样的情况。

假设只有一个 CPU 核心，两个线程 A、B 都需要执行 1000 万次 `counter++`，理论上最终结果应该是 `20000000`。

但问题在于：`counter++` 并不是一个原子操作，它需要经过读取、加一、写回三个步骤，而时钟中断可能发生在这些步骤之间。

假设初始 `counter = 0`：

1. 线程 A 执行：读取 `counter = 0`，计算得到 `1`，但还没写回内存。
    
2. 发生时钟中断：CPU 进入内核，操作系统保存线程 A 的执行状态，切换到线程 B。
    
3. 线程 B 执行：读取 `counter = 0`，加一后写回内存，此时 `counter = 1`。
    
4. 再次切换到线程 A：操作系统恢复线程 A 的执行状态，线程 A 将之前计算的 `1` 写回内存。
    
5. 最终结果：两个线程都执行了一次加一操作，但 `counter` 最终只等于 `1`，而不是 `2`。
    

_**这就是竞态条件（Race Condition）导致的丢失更新**_。

因此，当两个线程各执行 1000 万次 `counter++` 时，由于时钟中断可能引发线程切换，导致读取、修改、写入操作交错执行，部分更新可能丢失，所以最终结果不一定是 `20000000`。

一句话总结：时钟中断可能让线程在执行 `counter++` 的中途被切换，而 `counter++` 不是原子操作，因此两个线程可能基于同一个旧值进行修改，造成更新丢失。

补充一点：严格来说，原 C 程序还存在数据竞争，属于未定义行为；上述过程是帮助理解问题的典型执行场景。

#### 关键术语

- 临界区（critical section）是访问共享资源的一段代码，资源通常是一个变量或数据结构。
    
- **竞态条件（race condition）出现在多个执行线程大致同时进入临界区时，它们都试图更新共享的数据结构，导致了令人惊讶的（也许是不希望的）结果。**
    
- 不确定性（indeterminate）程序由一个或多个竞态条件组成，程序的输出因运行而异，具体取决于哪些线程在何时运行。这导致结果不是确定的（deterministic），而我们通常期望计算机系统给出确定的结果**。**
    

为了避免这些问题，线程应该使用某种互斥（mutual exclusion）原语。这样做可以保证只有一个线程进入临界区，从而避免出现竞态，并产生确定的程序输出。

### 第二十八章 锁

> _**锁（Lock）是操作系统和并发编程中用于实现互斥访问的一种同步机制。它的出现主要是为了解决多个线程并发访问共享资源时产生的竞态条件（Race Condition），保证共享数据的正确性。**_

### 1. 并发（Concurrency）

定义：并发是指多个任务在同一时间段内_**交替或重叠**_推进的执行方式，各任务的执行过程在时间上存在重叠，但不要求它们在同一时刻真正执行。

### 2. 竞态条件（Race Condition）

定义：竞态条件是指多个线程或执行主体在并发执行过程中，由于缺乏必要的同步约束，使程序的执行结果依赖于它们的执行时序或交错顺序，从而可能产生非预期结果的现象。

评价一个锁的实现的标准

1. 第一是锁是否能完成它的基本任务，即提供互斥（mutual exclusion）。
    
2. 第二是公平性（fairness）。当锁可用时，是否每一个竞争线程有公平的机会抢到锁？用另一个方式来看这个问题是检查更极端的情况：是否有竞争锁的线程会饿死（starve），一直无法获得锁？
    
3. 最后是性能（performance），具体来说，是使用锁之后增加的时间开销。
    

在操作系统中，锁的实现通常需要硬件和操作系统共同支持。两者的核心分工是：

- 硬件：提供原子操作能力，保证多个线程不能同时成功获取同一把锁。
    
- 操作系统：提供线程阻塞、唤醒和调度机制，避免线程在等待锁时一直浪费 CPU。
    

#### 一、硬件是如何支持锁的？

硬件主要提供三种支持方式。

##### 1. 关闭中断（Disabling Interrupts）

这是早期单处理器系统实现互斥的一种方式。

假设线程 A 正在执行临界区代码，操作系统暂时关闭当前 CPU 的可屏蔽中断：

```Plain
void lock() {
    DisableInterrupts();
}

void unlock() {
    EnableInterrupts();
}
```

由于单处理器上线程的抢占通常依赖时钟中断，因此关闭中断可以防止当前线程在临界区执行期间被定时器中断抢占。

但这种方式存在明显局限：

- **关闭中断可能影响系统对外部事件的响应。**
    
- **不能允许普通用户程序随意关闭中断。**
    
- **在多处理器系统中，关闭一个 CPU 的中断，并不能阻止其他 CPU 同时访问共享数据。**
    

因此，关闭中断主要适用于内核中某些非常短的临界区，而不是通用的用户态锁方案。

##### 2. 原子指令（Atomic Instructions）

这是现代锁实现最重要的硬件基础。

CPU 提供了一些特殊指令，能够保证读取和修改共享变量的操作具有原子性。

常见的原子操作包括：

|   |   |
|---|---|
|原子操作|作用|
|Test-and-Set|读取旧值并设置新值|
|Compare-and-Swap（CAS）|比较当前值，符合预期才更新|
|Fetch-and-Add|原子地读取并增加指定值|
|Exchange|原子地交换变量值|

以 Test-and-Set 为例：

```Plain
int TestAndSet(int *ptr) {
    int old = *ptr;
    *ptr = 1;
    return old;
}
```

以上只是伪代码，真实实现必须依赖硬件原子指令。

利用它就可以实现一个简单的自旋锁：

```Plain
int flag = 0;

void lock() {
    while (TestAndSet(&flag) == 1)
        ;
}

void unlock() {
    flag = 0;
}
```

当两个线程同时竞争锁时，CPU 保证它们对同一个锁变量的原子读-修改-写操作表现为按某个顺序执行，因此只有一个线程能获取成功。

这解决了锁最基本的正确性问题：互斥。

实际实现还需要合适的内存顺序约束，例如 acquire/release，确保临界区内的内存访问不会发生破坏同步语义的重排序。

##### 3. 缓存一致性机制（Cache Coherence）

在多处理器系统中，每个 CPU 核心通常拥有自己的缓存。

假设 CPU 1 和 CPU 2 都尝试修改同一个锁变量，硬件必须协调对这块共享内存的访问。

现代 CPU 可以通过缓存一致性协议（例如 MESI 及其变体）配合原子指令，保证针对同一缓存行的原子更新正确执行。

因此，在多核系统中，锁的正确实现不仅依赖原子指令，也依赖底层的缓存一致性和内存排序机制。

#### 二、操作系统是如何支持锁的？

硬件原子指令解决了互斥问题，但还存在一个问题：

**如果锁一直被其他线程占用，等待的线程应该怎么办？**

例如：

```Plain
while (TestAndSet(&flag) == 1)
    ;
```

这段代码会不断循环检查锁状态。

如果线程 A 持有锁 100ms，线程 B 可能持续占用 CPU 进行自旋，浪费计算资源。

因此，操作系统提供了更加高效的等待机制。

##### 1. 阻塞（Block）

当线程无法获取锁时，操作系统可以让它进入睡眠等待状态。

这样线程就不会继续占用 CPU 执行无意义的循环。

##### 2. 唤醒（Wakeup）

当持有锁的线程释放锁时，可以唤醒等待队列中的一个或多个线程。

被唤醒的线程重新成为可运行状态，等待调度器分配 CPU。

##### 3. 调度（Scheduling）

操作系统调度器决定哪个可运行线程获得 CPU。

注意，被唤醒并不意味着线程立即运行，也不意味着一定获得锁。它通常还需要重新竞争锁。

#### 三、硬件和操作系统如何协同实现锁？

以 Linux 上的互斥锁为例，其实现可以采用用户态原子操作 + 内核 Futex 等待机制。

第一，没有竞争时，获取锁可以完全在用户态完成。

#### 四、硬件和操作系统各自解决什么问题？

|   |   |   |
|---|---|---|
|维度|硬件支持|操作系统支持|
|核心目标|保证原子性与内存可见性、顺序约束|管理线程等待与调度|
|主要机制|CAS、Test-and-Set、原子交换|阻塞、唤醒、等待队列|
|实现互斥|提供基础原子操作|可以在其基础上实现同步原语|
|性能优化|避免非原子的竞争更新|避免长时间空转占用 CPU|
|典型应用|自旋锁|互斥锁、信号量等|

需要注意，操作系统不是所有锁都必须参与的。例如纯用户态自旋锁，可以主要依靠硬件原子操作实现；只有需要阻塞和唤醒等服务时，才需要内核介入。

建议重点掌握从 `Test-and-Set` 自旋锁到 `yield()`，再到基于等待队列的 `park()/unpark()` 这条演进路线。它能很好地解释为什么只有原子指令还不够，以及操作系统为什么需要提供阻塞和唤醒机制。

### 第二十九章：基于锁的并发数据结构

并发（Concurrency）：多个任务在一段时间内交替推进。

并行（Parallelism）：多个任务在同一时刻实际执行。

> 本章讨论的是如何把原本只能在单线程环境下安全使用的数据结构，改造成能够被多个线程并发访问的数据结构，同时尽可能保证性能。
> 
> 我认为核心是：数据结构的并发数据（也就是锁）的_**粒度**_ 对
> 
> - 正确性（Correctness）：多个线程并发访问数据结构时，能否保证数据的一致性？
>     
> - 性能（Performance）：能否避免线程过度争抢同一把锁，让多个 CPU 核心真正发挥作用？
>     

#### 并发计数器（Concurrent Counter）

最简单的解决方法就是给计数器加锁：

```C++
typedef struct __counter_t {
    int value;
    pthread_mutex_t lock;
} counter_t;

void increment(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    c->value++;
    pthread_mutex_unlock(&c->lock);
}
```

加锁之后，程序虽然正确了，但它的并发性能怎么样？很遗憾的是同步的计数器扩展性不好。单线程完成100万次更新只需要很短的时间（大约0.03s），而两个线程并发执行，每个更新100万次，性能下降很多（超过5s！）。线程更多时，性能更差。

而这就是涉及到 _**锁的粒度**_ 的范围了。**懒惰计数器（sloppy counter）**是我们思想的体现。

懒惰计数器（Sloppy Counter） 其核心思想是

- 将一个全局计数器拆分为多个局部计数器，通常每个 CPU 核心对应一个局部计数器，每个局部计数器都有独立的互斥锁，同时维护一个由全局锁保护的全局计数器。
    
- 线程执行递增操作时，优先获取对应局部计数器的锁并更新局部值，而不是每次都争抢全局锁。当局部计数器的值达到指定阈值 `S` 时，线程才获取全局锁，将局部累计值批量合并到全局计数器，并清空局部计数器。
    
- 这种设计通过减少全局锁的获取次数、降低线程之间的锁竞争，提高了多核环境下的并发性能。但代价是全局计数器的值可能暂时落后于实际计数总和，而且阈值 `S` 越大，全局计数器更新越不及时。

##### 一、为什么给数据结构加上一把全局锁，就能解决很多并发正确性问题？

理解和解答这个问题首先要明白并发是怎么产生的：

假设有两个线程同时执行

```Plain
counter->value++;
```

这条语句看起来只有一步，但底层可以抽象成三个操作：

```Plain
LOAD  R1, [value]   ; 读取 value
ADD   R1, R1, 1     ; 加 1
STORE [value], R1   ; 写回 value
```

假设 `value = 0`，两个线程在不同 CPU 核心上并行执行：

终 `value = 1`，但正确结果应该是 `2`。_**这就是典型的竞态条件（Race Condition），具体表现为丢失更新。**_

全局锁如何解决？我们在操作前获取锁：

```Plain
void increment(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    c->value++;
    pthread_mutex_unlock(&c->lock);
}
```

_**由于互斥锁保证同一时刻最多只有一个线程持有这把锁**_，因此两个线程不能同时进入受保护的临界区。

_**因此，全局锁解决问题的本质，是通过互斥访问，把原本可能交错执行的临界区变成串行执行。**_

##### 二、为什么增加线程数量，程序吞吐量不一定提高，甚至可能下降？

首先区分两个概念：

- 并发（Concurrency）：多个任务在一段时间内交替推进。
    
- 并行（Parallelism）：多个任务在同一时刻实际执行。
    

**增加线程数量，提高的是潜在的并发程度**，并不意味着能够增加实际并行执行的工作量。假设有一个全局计数器，所有线程都需要获取同一把锁才能修改它，即使 CPU 有 16 个核心，**同一时刻仍然只能有一个线程执行计数器的临界区**。这意味着锁成为了整个程序的串行瓶颈。

除了临界区无法并行之外，线程越多，还可能产生更多额外开销。

1. 锁竞争：更多线程同时争抢锁，等待时间增加。
    
2. 上下文切换：当线程因锁竞争而阻塞、唤醒时，可能产生调度和上下文切换开销。
    
3. 缓存一致性开销：在多核 CPU 中，锁所在的缓存行可能频繁在不同核心之间转移，造成额外的缓存一致性通信。
    
4. 调度开销：当可运行线程超过 CPU 能够同时执行的线程数量时，操作系统需要进行更多调度。
    

##### 三、为什么把一把全局锁拆成多把局部锁，有时候能提升性能，有时候反而会降低性能？

1. 为什么多把局部锁能够提高性能？
    

使用全局锁时：

```Plain
pthread_mutex_lock(&global_lock);
global_counter++;
pthread_mutex_unlock(&global_lock);
```

假设有四个线程，它们都需要争抢 `global_lock`。

而使用局部锁之后：

```Plain
pthread_mutex_lock(&local_lock[id]);
local_counter[id]++;
pthread_mutex_unlock(&local_lock[id]);
```

不同线程可以修改不同的局部计数器。

![](https://hcnz58qdrv4l.feishu.cn/space/api/box/stream/download/asynccode/?code=YjA0MmFlM2VkNmUwNzFiNWNiYWEwNzY2MDFmZmRhMmZfZVN4VFRoQnVXTHVuM0U4cWIyWUt4S1k4YUlaM2s1bjBfVG9rZW46R1N0WWJuWWYxb0ljdm14Y1N2aGNCcnNHbkpjXzE3OTQxMjY2OTk6MTc5NDEzMDI5OV9WNA&add_watermark=true&scene_type=CCM)

**这样就把原来集中在同一把锁上的竞争分散到了多把锁上，减少线程等待时间**。

2. 为什么多把锁也可能降低性能？
    

**首先，多把锁意味着更多的锁管理操作和更复杂的同步逻辑**。

例如在并发链表中，如果为每个节点单独设置一把锁，那么一次遍历操作可能需要反复获取和释放不同节点上的锁。相对于只获取一次全局锁，这些操作可能产生更高的开销。

其次，**细粒度锁只有在不同线程能够访问不同资源时，才容易发挥优势**。假设四个线程虽然使用了不同的局部锁，但最后都需要频繁获取同一把全局锁合并数据，那么竞争依然存在。

### 第三十章 条件变量

**条件变量（Condition Variable）：是一种用于线程间同步的机制**，它允许线程在某个共享条件不满足时，原子地释放互斥锁并进入等待状态，直到被其他线程通知后重新获取锁、检查条件，从而实现线程之间高效的等待与唤醒，避免忙等待造成的 CPU 资源浪费。

核心作用： 配合互斥锁，实现线程之间基于共享状态的等待与通知。条件变量不是条件本身，它只是线程等待和接收通知的机制。

在上一章，我们学习了锁。锁主要解决的是互斥问题：多个线程同时访问共享资源时，如何避免竞态条件。

**但是锁无法直接解决线程之间的等待问题**。

例如，父线程必须等待子线程完成：

```Plain
while (done == 0) {
    // 不断检查子线程是否完成
}
```

这种方式称为忙等待（Busy Waiting），它会持续消耗 CPU 资源。

条件变量的出现就是为了解决这个问题：**当条件不满足时，线程可以主动进入睡眠等待；当其他线程改变共享状态时，再通知等待线程**。

```C++
#include <stdio.h>
#include <pthread.h>

// 共享状态变量：
// done = 0：子线程尚未完成任务
// done = 1：子线程已经完成任务
int done = 0;

// 互斥锁：保护共享变量 done，
// 同时配合条件变量保证检查条件和进入等待的过程正确进行
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

// 条件变量：
// 当 done == 0 时，父线程可以通过它进入等待状态
// 子线程完成任务后，通过它通知正在等待的父线程
pthread_cond_t c = PTHREAD_COND_INITIALIZER;

// 子线程完成任务后调用
void thr_exit(void) {
    // 1. 获取互斥锁，准备修改共享变量 done
    pthread_mutex_lock(&m);

    // 2. 修改共享状态，表示子线程已经完成
    done = 1;

    // 3. 发送信号，通知等待在条件变量 c 上的线程
    // 注意：signal 不会直接释放互斥锁
    // 如果父线程被唤醒，仍然需要重新获取 m 才能继续执行
    pthread_cond_signal(&c);

    // 4. 释放互斥锁
    // 此时被唤醒的父线程才有机会获取锁，重新检查 done
    pthread_mutex_unlock(&m);
}

// 子线程执行的函数
void *child(void *arg) {
    printf("child\n");

    // 子线程完成任务，更新 done 并通知父线程
    thr_exit();

    return NULL;
}

// 父线程调用该函数，等待子线程完成
void thr_join(void) {
    // 1. 获取互斥锁，确保安全读取 done
    pthread_mutex_lock(&m);

    // 2. 检查子线程是否完成
    // 必须使用 while，而不是 if
    // 因为条件变量允许虚假唤醒，醒来后必须重新检查条件
    while (done == 0) {
        // pthread_cond_wait 会原子地完成两件事：
        // ① 释放互斥锁 m
        // ② 进入条件变量 c 的等待状态
        //
        // 释放锁非常重要：
        // 如果父线程等待时一直持有锁，
        // 子线程就无法获取锁修改 done，从而导致死锁
        //
        // 被唤醒后，pthread_cond_wait 会先重新获取 m，
        // 然后才返回，继续执行 while 条件判断
        pthread_cond_wait(&c, &m);
    }

    // 3. 此时 done == 1，说明子线程已经完成
    // 释放互斥锁，让其他线程能够访问共享状态
    pthread_mutex_unlock(&m);
}

int main(void) {
    printf("parent: begin\n");

    pthread_t p;

    // 1. 创建子线程
    // 子线程从 child() 开始执行
    pthread_create(&p, NULL, child, NULL);

    // 2. 父线程等待子线程完成
    // 如果 done == 0，父线程会进入等待状态
    // 如果 done == 1，父线程不会等待
    thr_join();

    // 3. 只有确认 done == 1 后，才执行下面的代码
    printf("parent: end\n");

    // 使用真正的 pthread_join 回收子线程资源
    // thr_join() 只是通过条件变量模拟等待完成的行为
    pthread_join(p, NULL);

    // 销毁同步对象
    pthread_cond_destroy(&c);
    pthread_mutex_destroy(&m);

    return 0;
}
```

#### 为什么条件变量必须与互斥锁配合

1. 假设我们没有互斥锁代码变成：
    

```Plain
while (done == 0)
    wait(&c);
```

可能出现下面的执行顺序：

|   |   |   |
|---|---|---|
|时间|父线程|子线程|
|T1|检查 done == 0||
|T2|被操作系统暂停||
|T3||将 done = 1|
|T4||调用 signal()|
|T5|恢复执行，调用 wait()||
|T6|永久等待，无法结束|已结束|

这种情况称为 **丢失唤醒（Lost Wakeup）**。

**因为子线程发出通知时，父线程还没有真正进入等待状态。条件变量不会将这次通知保存起来，供将来的** **`wait()`** **消费**。

那么互斥锁如何解决这个问题？

关键在于 `pthread_cond_wait(&c, &m)` 会**原子**地释放锁并开始等待。

_**这就保证子线程不可能在父线程检查完**_ _**`done == 0`**_ _**后、进入等待之前，抢先获取锁并完成通知。**_

反过来，如果子线程先执行完成，将 `done = 1`，父线程之后获取锁会发现条件已经满足，直接跳过等待。

两种执行顺序都能够正确工作。

#### 生产者消费者问题

假设存在一个共享缓冲区：

- 生产者负责向缓冲区放入数据。
    
- 消费者负责从缓冲区取出数据。
    

生产者需要在缓冲区满时等待，消费者需要在缓冲区空时等待。最初代码：

```C++
cond_t cond; // 条件变量
mutex_t mutex; // 互斥锁

void *producer(void *arg) {
    Pthread_mutex_lock(&mutex);
    if (count == 1)
        Pthread_cond_wait(&cond, &mutex);
    put(1);
    Pthread_cond_signal(&cond);
    Pthread_mutex_unlock(&mutex);
    return NULL;
}

void *consumer(void *arg) {
    Pthread_mutex_lock(&mutex);
    if (count == 0)
        Pthread_cond_wait(&cond, &mutex);
    int tmp = get();
    Pthread_cond_signal(&cond);
    Pthread_mutex_unlock(&mutex);
    return NULL;
}
```

这一部分的核心是理解三个问题：

##### 为什么使用 `if` 判断条件会出错？

原因：**线程被唤醒后，原本满足的条件可能已经不成立。**

例如：

1. 消费者 C1 发现缓冲区为空，进入等待。
    
2. 生产者 P 放入一个数据，唤醒 C1。
    
3. 但 C1 还没执行，消费者 C2 抢先取走了数据。
    
4. C1 恢复执行，由于 `if` 不会重新检查条件，直接取数据，导致错误。
    

修复：使用 `while` 代替 `if`，线程被唤醒后重新检查条件，不满足就继续等待。

##### 为什么改成 `while` 之后仍然可能出错？

原因：生产者和消费者使用同一个条件变量，可能唤醒错误的线程，最终导致所有线程都在等待。

例如：

1. C1、C2 因缓冲区为空而等待。
    
2. P 生产一个数据，唤醒 C1。
    
3. P 再次生产时发现缓冲区已满，也进入等待。
    
4. C1 消费数据后调用 `signal()`，却唤醒了 C2，而不是 P。
    
5. C2 发现缓冲区仍为空，继续等待，最终所有线程都陷入等待。
    

修复：将生产者和消费者的等待条件分开，使用两个条件变量。

##### 为什么最终需要两个条件变量？

原因：生产者和消费者等待的是不同的条件，需要分别通知。

- `empty`：生产者等待缓冲区出现空位，由消费者唤醒。
    
- `fill`：消费者等待缓冲区出现数据，由生产者唤醒。
    

最终实现：

```C
// 生产者
pthread_mutex_lock(&mutex);
while (count == MAX)
    pthread_cond_wait(&empty, &mutex);
put(value);
pthread_cond_signal(&fill);
pthread_mutex_unlock(&mutex);

// 消费者
pthread_mutex_lock(&mutex);
while (count == 0)
    pthread_cond_wait(&fill, &mutex);
int value = get();
pthread_cond_signal(&empty);
pthread_mutex_unlock(&mutex);
```

#### 从单槽缓冲区扩展到有界缓冲区

之前只能放一个数据，后来可以放多个，例如：

```Java
int buffer[MAX];
int fill_ptr = 0;
int use_ptr = 0;
int count = 0;

// 向缓冲区放入数据
void put(int value) {
    buffer[fill_ptr] = value;
    fill_ptr = (fill_ptr + 1) % MAX;
    count++;
}

// 从缓冲区取出数据
int get() {
    int tmp = buffer[use_ptr];
    use_ptr = (use_ptr + 1) % MAX;
    count--;
    return tmp;
}

cond_t empty, fill;
mutex_t mutex;

// 生产者线程
void *producer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);             // p1
        while (count == MAX)                    // p2
            Pthread_cond_wait(&empty, &mutex);  // p3
        put(i);                                 // p4
        Pthread_cond_signal(&fill);             // p5
        Pthread_mutex_unlock(&mutex);           // p6
    }
    return NULL;
}

// 消费者线程
void *consumer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);             // c1
        while (count == 0)                      // c2
            Pthread_cond_wait(&fill, &mutex);   // c3
        int tmp = get();                        // c4
        Pthread_cond_signal(&empty);            // c5
        Pthread_mutex_unlock(&mutex);           // c6
        printf("%d\n", tmp);
    }
    return NULL;
}
```

#### 课后提问

##### 一、为什么已经有互斥锁，还需要条件变量？`pthread_cond_wait()` 的工作原理是什么？

**因为互斥锁解决的是线程之间的互斥访问问题，而条件变量解决的是线程之间的等待与通知问题。**

- 互斥锁：保证同一时刻只有一个线程访问共享资源，避免竞态条件。
    
- **条件变量：当某个条件不满足时，让线程进入睡眠等待，等其他线程改变条件后再唤醒它，避免忙等待浪费 CPU。**
    

例如生产者—消费者问题中，互斥锁保证缓冲区不会被多个线程同时修改，而条件变量让消费者在缓冲区为空时等待，直到生产者放入数据。

`pthread_cond_wait()` 的工作原理是什么？

```C
pthread_mutex_lock(&mutex);

while (count == 0) {
    pthread_cond_wait(&cond, &mutex);
}

pthread_mutex_unlock(&mutex);
```

`pthread_cond_wait()` 主要经历三个过程：

1. **释放锁并进入等待**：原子地释放互斥锁，同时进入条件变量的等待状态，避免丢失唤醒。
    
2. **等待其他线程通知**：线程进入阻塞等待，不再持续占用 CPU。
    
3. **被唤醒后重新获取锁**：收到通知后，必须重新获得互斥锁，才能从 `wait()` 返回，并通过 `while` 再次检查条件。
    

##### 二、为什么条件变量必须使用 `while` 而不是 `if`？为什么 `signal()` 不意味着等待条件已经满足？

_**因为线程被唤醒后，原本等待的条件可能已经不成立。**_例如生产者—消费者问题：

1. 消费者 C1 发现缓冲区为空，进入等待。
    
2. 生产者 P 放入一个数据，调用 `signal()` 唤醒 C1。
    
3. 但 C1 还没运行，消费者 C2 就抢先取走了数据。
    
4. C1 恢复执行，此时缓冲区已经为空。
    

如果使用 `if`，C1 不会重新检查条件，直接取数据，导致错误。

如果使用 `while`，C1 会重新检查缓冲区是否为空，如果为空就继续等待。

```Plain
// 错误：只检查一次
if (count == 0)
    pthread_cond_wait(&cond, &mutex);

// 正确：每次被唤醒后重新检查
while (count == 0)
    pthread_cond_wait(&cond, &mutex);
```

为什么 `signal()` 不意味着等待条件已经满足？因为 POSIX 条件变量采用 Mesa 语义。

_**`signal()`**_ _**只是通知等待线程可以尝试继续执行，并不保证被唤醒的线程立即运行，也不保证它重新获得锁时条件仍然成立。**_

另外，条件变量还允许出现虚假唤醒，即没有收到明确通知也可能从 `wait()` 返回。

##### 三、为什么生产者—消费者问题使用一个条件变量可能导致死锁？最终是如何解决的？

**因为生产者和消费者等待的是不同的条件，但使用同一个条件变量时，****`signal()`** **可能唤醒错误类型的线程，导致所有线程都进入等待状态**。

例如，有一个生产者 P 和两个消费者 C1、C2：

1. C1、C2 发现缓冲区为空，都进入等待。
    
2. P 生产一个数据，调用 `signal()` 唤醒 C1。
    
3. P 再次生产，发现缓冲区已满，也进入等待。
    
4. C1 消费数据后调用 `signal()`，却唤醒了 C2，而不是 P。
    
5. C2 发现缓冲区仍为空，重新进入等待。此时 C1 也在下一轮消费中等待。
    

最终，P、C1、C2 全部处于等待状态，没有线程能够继续执行，形成死锁。

最终通过使用两个条件变量来解决的。

### 第三十一章 信号量

信号量（Semaphore）: 是操作系统中用于实现线程同步与互斥的一种同步原语。

它通过维护一个整数计数值来管理可用资源或许可的数量，并提供两个原子操作：`sem_wait()`（P 操作）和 `sem_post()`（V 操作）。当线程申请许可但没有可用许可时，会被阻塞；当其他线程释放许可时，等待的线程可以被唤醒，从而实现对共享资源的并发访问控制以及线程之间的执行顺序协调。

> 如果说前面几章的锁、条件变量主要是介绍不同的并发控制机制，那么这一章的核心就是：
> 
> 能不能使用一种统一的同步原语，同时解决互斥访问和线程之间的执行顺序问题？
> 
> 答案就是信号量。

#### 基本原理

信号量本质上是一个用于线程同步的对象，可以**把它理解为一个整数状态，加上两个原子操作，以及必要的等待与唤醒机制**。

POSIX 信号量提供两个最重要的操作：

```Plain
sem_wait(&s);
sem_post(&s);
```

`sem_wait()` 通常也叫 P 操作，`sem_post()` 通常也叫 V 操作。

- `sem_wait()`：尝试获取一个许可。如果有可用许可，就消耗一个并继续执行；否则等待。
    
- `sem_post()`：释放一个许可，如果有线程正在等待，可能唤醒其中一个线程。
    

信号量用作条件变量的简单例子：信号量只会在值小于0时等待。（关系信号量的初始值的设定至关重要，下面是设置为0）

```C++
sem_t s;

void *child(void *arg) {
    printf("child\n");
    sem_post(&s);
    return NULL;
}

int main() {
    pthread_t p;
    sem_init(&s, 0, 0);
    pthread_create(&p, NULL, child, NULL);

    sem_wait(&s);
    printf("parent\n");
    pthread_join(p, NULL);
    sem_destroy(&s);
    return 0;
}
```

#### 生产者—消费者问题

假设生产者不断向缓冲区写入数据，消费者不断从缓冲区读取数据。

这里需要同时解决两个问题：缓冲区不能被同时修改，并且生产者不能往满缓冲区写入，消费者不能从空缓冲区读取。

因此，通常需要三个信号量：

|   |   |   |
|---|---|---|
|信号量|初始值|作用|
|mutex|1|保证缓冲区访问互斥|
|empty|N|记录剩余空槽数量|
|full|0|记录已经填充的槽数量|

这一部分的重点不仅是理解如何使用三个信号量，**还要理解为什么** **`sem_wait()`** **的调用顺序不正确，会产生死锁**。

```C++
#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>

// 三个信号量
sem_t empty;  // 记录缓冲区中空闲位置的数量
sem_t full;   // 记录缓冲区中已有数据的数量
sem_t mutex;  // 互斥信号量，保护共享缓冲区

// 生产者线程
void *producer(void *arg) {
    int i;

    for (i = 0; i < loops; i++) {
        // 1. 等待空闲缓冲区
        // 如果 empty == 0，说明缓冲区已满，生产者阻塞
        sem_wait(&empty);

        // 2. 获取互斥锁，进入临界区
        // 确保同一时刻只有一个线程操作缓冲区
        sem_wait(&mutex);

        // 3. 向共享缓冲区写入数据
        put(i);

        // 4. 释放互斥锁，退出临界区
        sem_post(&mutex);

        // 5. 通知消费者：缓冲区新增了一个数据
        // full 增加 1，可能唤醒等待中的消费者
        sem_post(&full);
    }

    return NULL;
}

// 消费者线程
void *consumer(void *arg) {
    int i;

    for (i = 0; i < loops; i++) {
        // 1. 等待缓冲区中存在数据
        // 如果 full == 0，说明缓冲区为空，消费者阻塞
        sem_wait(&full);

        // 2. 获取互斥锁，进入临界区
        // 防止多个线程同时修改共享缓冲区
        sem_wait(&mutex);

        // 3. 从共享缓冲区取出数据
        int tmp = get();

        // 4. 释放互斥锁，退出临界区
        sem_post(&mutex);

        // 5. 通知生产者：缓冲区新增了一个空闲位置
        // empty 增加 1，可能唤醒等待中的生产者
        sem_post(&empty);

        // 6. 输出消费的数据
        printf("%d\n", tmp);
    }

    return NULL;
}

int main(int argc, char *argv[]) {
    // 初始化信号量
    // 第二个参数为 0，表示在线程之间共享

    // 初始有 MAX 个空闲缓冲区位置
    sem_init(&empty, 0, MAX);

    // 初始没有任何可消费的数据
    sem_init(&full, 0, 0);

    // 初始互斥锁可用，相当于一把二元信号量锁
    sem_init(&mutex, 0, 1);

    // 此处省略线程创建、等待以及资源清理代码
    // ...

    return 0;
}
```

#### 读者—写者问题

假设多个线程共享一份数据：

- 多个读者可以同时读取。
    
- 写者必须独占数据，不能与其他读者或写者同时访问。
    

关键是：**第一个读者负责阻止写者进入，最后一个读者负责允许写者进入**。

```C++
#include <semaphore.h>

// 读写锁结构体
typedef struct _rwlock_t {
    sem_t lock;       // 互斥信号量，保护 readers 计数器
    sem_t writelock;  // 读写互斥：允许一个写者或多个读者
    int readers;      // 当前正在读取共享资源的读者数量
} rwlock_t;

// 初始化读写锁
void rwlock_init(rwlock_t *rw) {
    rw->readers = 0;

    // 初始化为 1，表示计数器的互斥锁可用
    sem_init(&rw->lock, 0, 1);

    // 初始化为 1，表示共享资源当前可以被访问
    sem_init(&rw->writelock, 0, 1);
}

// 获取读锁
void rwlock_acquire_readlock(rwlock_t *rw) {
    // 1. 获取互斥锁，保护 readers 的修改
    sem_wait(&rw->lock);

    // 2. 读者数量加 1
    rw->readers++;

    // 3. 如果是第一个读者，需要获取 writelock
    // 阻止写者进入临界区
    if (rw->readers == 1) {
        sem_wait(&rw->writelock);
    }

    // 4. 释放计数器互斥锁
    // 后续读者可以继续进入，不需要重复获取 writelock
    sem_post(&rw->lock);
}

// 释放读锁
void rwlock_release_readlock(rwlock_t *rw) {
    // 1. 获取互斥锁，保护 readers 的修改
    sem_wait(&rw->lock);

    // 2. 读者数量减 1
    rw->readers--;

    // 3. 如果是最后一个读者，释放 writelock
    // 允许等待中的写者获取共享资源
    if (rw->readers == 0) {
        sem_post(&rw->writelock);
    }

    // 4. 释放计数器互斥锁
    sem_post(&rw->lock);
}

// 获取写锁
void rwlock_acquire_writelock(rwlock_t *rw) {
    // 获取 writelock
    // 如果存在读者或其他写者，则阻塞等待
    sem_wait(&rw->writelock);
}

// 释放写锁
void rwlock_release_writelock(rwlock_t *rw) {
    // 释放 writelock
    // 允许等待中的读者或写者继续竞争共享资源
    sem_post(&rw->writelock);
}
```

#### 信号量的实现

最后，我们用底层的同步原语（锁和条件变量），来实现自己的信号量，名字叫作Zemaphore。这个任务相当简单。

```C++
#include <pthread.h>

// 使用互斥锁和条件变量实现信号量
typedef struct _Zem_t {
    int value;            // 信号量计数值，表示当前可用资源数量
    pthread_cond_t cond;  // 条件变量，用于阻塞和唤醒等待资源的线程
    pthread_mutex_t lock; // 互斥锁，保护 value 的并发访问
} Zem_t;

// 初始化信号量
// 要求初始化时只有一个线程调用，避免并发初始化
void Zem_init(Zem_t *s, int value) {
    // 1. 设置初始资源数量
    s->value = value;

    // 2. 初始化条件变量
    Cond_init(&s->cond);

    // 3. 初始化互斥锁
    Mutex_init(&s->lock);
}

// P 操作：等待并获取资源
void Zem_wait(Zem_t *s) {
    // 1. 获取互斥锁，保护 value
    Mutex_lock(&s->lock);

    // 2. 检查是否存在可用资源
    // 如果 value <= 0，说明没有可用资源
    while (s->value <= 0) {
        // 原子地释放互斥锁并进入等待状态
        // 被唤醒后，重新获取互斥锁，再次检查条件
        Cond_wait(&s->cond, &s->lock);
    }

    // 3. 获取一个资源，计数器减 1
    s->value--;

    // 4. 释放互斥锁
    Mutex_unlock(&s->lock);
}

// V 操作：释放资源并通知等待线程
void Zem_post(Zem_t *s) {
    // 1. 获取互斥锁，保护 value
    Mutex_lock(&s->lock);

    // 2. 释放一个资源，计数器加 1
    s->value++;

    // 3. 唤醒一个等待在条件变量上的线程
    // 注意：被唤醒的线程不会立即执行
    // 必须重新获得互斥锁，并检查 value 是否大于 0
    Cond_signal(&s->cond);

    // 4. 释放互斥锁
    Mutex_unlock(&s->lock);
}
```

#### 课后提问

##### 一、解释 sem_wait() 和 sem_post() 如何协调多个线程？

`sem_wait()` 和 `sem_post()` 通过**信号量的计数值，以及线程的阻塞和唤醒机制来协调多个线程的执行**。

你可以把信号量理解为一个记录“剩余许可数量”的计数器。

- `sem_wait()`：申请一个许可。如果有许可，就消耗一个并继续执行；如果没有（计数值为0），就阻塞等待。
    
- `sem_post()`：释放一个许可，使许可重新可用，并在有等待线程时唤醒其中一个。
    

##### 二、解释信号量初始值为 0、1、N 分别意味着什么？

信号量的初始值表示一开始有多少个可用许可（Permit）。不同的初始值，决定了线程是否需要等待，以及最多允许多少个线程同时获取许可。

|   |   |   |
|---|---|---|
|初始值|含义|典型应用|
|0|没有可用许可，线程必须等待其他线程释放许可|线程同步、控制执行顺序|
|1|有一个许可，最多允许一个线程持有许可|互斥访问共享资源|
|N|有 N 个许可，最多允许 N 个线程同时持有许可|资源池、限制并发数量|

1. 初始值为 0：用于线程同步
    

```Plain
sem_t sem;
sem_init(&sem, 0, 0);

// 线程 A
printf("A 完成任务\n");
sem_post(&sem);

// 线程 B
sem_wait(&sem);
printf("B 开始执行\n");
```

信号量初始化为 `0`，意味着没有可用许可。

假设线程 B 先执行，调用 `sem_wait()` 时会阻塞，直到线程 A 调用 `sem_post()` 释放一个许可，B 才能继续执行。

如果 A 先执行，许可会被保留下来，B 之后调用 `sem_wait()` 可以直接通过。

因此，初始值为 0，通常用于保证某个操作必须在另一个操作完成之后才能执行。

2. 初始值为 1：用于互斥
    

```Plain
sem_t sem;
sem_init(&sem, 0, 1);

void *worker(void *arg) {
    sem_wait(&sem);

    // 临界区：访问共享资源
    counter++;

    sem_post(&sem);
    return NULL;
}
```

信号量初始化为 `1`，意味着只有一个许可。

第一个线程调用 `sem_wait()` 后，许可数量变成 `0`，其他线程必须等待。直到第一个线程调用 `sem_post()`，其他线程才有机会获得许可。

因此，初始值为 1，可以实现互斥，保证同一时刻最多一个线程进入受保护的临界区。

3. 初始值为 N：用于限制并发数量
    

假设系统有 3 个数据库连接，只允许最多 3 个线程同时占用连接。

```Plain
sem_t sem;
sem_init(&sem, 0, 3);

void *worker(void *arg) {
    sem_wait(&sem);

    // 使用一个数据库连接
    use_database();

    sem_post(&sem);
    return NULL;
}
```

由于只有 3 个许可，因此最多允许 3 个线程同时使用连接，剩下的线程需要等待。

因此，初始值为 N，通常用于控制最多 N 个线程同时使用某类有限资源。

你需要区分两个概念：

- 互斥（Mutual Exclusion）：解决多个线程不能同时访问某个资源的问题，典型初始值为 `1`。
    
- 同步（Synchronization）：解决线程之间执行顺序的问题，典型初始值为 `0`。
    

而初始值为 `N` 的计数信号量，则可以看作对多个相同资源的并发使用进行数量限制。

**注意，初始值只是起点，不是信号量永远不能超过的上限**。如果线程不断调用 `sem_post()` 而没有对应的 `sem_wait()`，计数还可能继续增长（直到实现允许的最大值）。

_**一句话总结：信号量初始化为 0，侧重等待事件；初始化为 1，常用于互斥；初始化为 N，常用于限制并发访问数量。**_

##### 三、能否说明读者—写者问题中的饥饿，以及哲学家就餐问题中的死锁？

- 读者—写者问题中的饥饿（Starvation）：在读者优先的实现中，多个读者可以同时读取共享资源，但写者必须等待所有读者结束。如果不断有新的读者进入，写者就可能一直无法获得资源，长期处于等待状态，这就是饥饿。
    
- 哲学家就餐问题中的死锁（Deadlock）：假设五个哲学家吃饭时都先拿起左边的叉子，再尝试拿右边的叉子。当所有哲学家都拿到了左边的叉子时，每个人都在等待右边的叉子被释放，形成循环等待，导致所有哲学家都无法继续执行，这就是死锁。两者的核心区别是：饥饿是某个线程长期得不到资源，而其他线程仍可能继续执行；死锁是多个线程相互等待，导致相关线程都无法继续执行。

### 第三十二章 常见并发问题

> 由并发引起的问题主要有两种：非死锁问题/死锁问题

- 非死锁问题：又分为违反原子性错误（通过互斥锁解决）和违反顺序错误（通过条件变量解决）
    
- 死锁问题：
    
    - 互斥：线程对于需要的资源进行互斥的访问（例如一个线程抢到锁）。
        
    - 持有并等待：线程持有了资源（例如已将持有的锁），同时又在等待其他资源（例如，需要获得的锁）。
        
    - 非抢占：线程获得的资源（例如锁），不能被抢占。
        
    - 循环等待：线程之间存在一个环路，环路上每个线程都额外持有一个资源，而这个资源又是下一个线程要申请的。
