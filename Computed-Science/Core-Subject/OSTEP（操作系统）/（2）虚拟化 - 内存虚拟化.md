> 用户程序生成的每个地址都是虚拟地址（every address generated by a user program is a virtual address）。

### 第十三章 抽象：地址空间

_**地址空间**__**，就是**__**操作系统**__**给一个进程看到的“它能使用的**__**内存**__**地址范围”**_。注意，这个“地址”首先是**虚拟地址**，不等于真实物理内存地址。

#### 地址空间的必要性

假设存在两个进程如果没有地址空间，两个进程都直接访问真实物理内存：那会有一个很严重的问题：Process A 写 0x1000，Process B 也写 0x1000 它们可能直接把对方的数据覆盖掉。更危险的是，用户程序可以直接访问任意物理内存，甚至会修改操作系统内核。地址空间存在的主要目的：_**OS**_ _**不希望程序直接看到真实物理内存，而是给每个进程创建一个自己的**__**内存**__**世界**_。

#### 地址空间的组成

一个典型进程的虚拟地址空间，大概可以理解为：

- Heap 堆：申请的内存一般来自heap
    
- Stack栈：局部变量、函数调用信息等通常放在 stack。
    

地址空间和虚拟内存系统的存在主要解决了操作系统三个主要问题

- _**隔离/透明**__：程序的行为就好像它拥有自己的私有__物理内存__。每个进程都认为整个“__内存__空间是我的”_
    
- _**效率**__：时间上（即不会使程序运行得更慢）和空间上（即不需要太多额外的__内存__来支持虚拟化）_
    
- _**保护**__：虚拟内存限制了进程之间内存的相互访问，同时也防止了进程对操作系统的修改_

### 第十五章 机制：地址转换

> 虚拟现实的背后是丑陋的物理事实。

我们利用了一种通用技术，被称为_**基于硬件的地址转换（hardware-based address translation）**_，简称为地址转换（address translation）来实现灵活高效的实现虚拟化内存。

_**“基于硬件的地址转换”本质上就是：CPU 发出的虚拟地址，不直接访问内存，而是由硬件先转换成物理地址，再去访问真正的内存**_。这里最关键的硬件叫 **MMU（Memory Management Unit，内存管理单元）**

#### 动态重定位

在20世纪50年代后期，它在首次出现的时分机器中引入，那时只是一个简单的思想，称为_**基址加界限机制（base and bound）**_，有时又称为_**动态重定位（dynamic relocation）**_。具体来说，每个CPU需要两个硬件寄存器：_**基址（base）寄存器和界限（bound）寄存器**_，有时称为限制（limit）寄存器。

求取物理地址公式：

```JavaScript
physical address = virtual address + base
```

有人可能会问那么界限寄存器又是在干什么：界限寄存器提供了访问保护，假设界限寄存器被置为16KB。如果进程需要访问超过这个界限或者为负数的虚拟地址，CPU将触发异常，进程最终可能被终止。_**界限寄存器的用处在于，它确保了进程产生的所有地址都在进程的地址“界限”中。**_

由于这种重定位是在运行时发生的，而且我们甚至可以在进程开始运行后改变其地址空间，这种技术一般被称为_**动态**_重定位（dynamic relocation）。

#### Base + Bounds 的严重问题

它要求一个进程必须占据：一整块连续物理内存。如果由于该进程的栈区和堆区并不很大，导致这块内存区域中大量的空间被浪费。这种浪费通常称为_**内部碎片（internal fragmentation）**_，指的是已经分配的内存单元内部有未使用的空间（即碎片），造成了浪费。

### 第十六章 分段

> 分段就是把进程的虚拟地址空间按照 Code、Heap、Stack 等逻辑区域划分为多个可变大小的段，每个段都有独立的 Base、Bounds 和权限信息，MMU 根据段号和段内偏移完成地址转换。

利用**基址和界限寄存器**，操作系统很容易将不同进程重定位到不同的物理内存区域。但是，对于这些内存区域，你可能已经注意到一件有趣的事：_**栈和堆之间，有一大块“空闲”空间**_。_**为了解决这个问题，分段（segmentation）的概念应运而生。**_

![](https://hcnz58qdrv4l.feishu.cn/space/api/box/stream/download/asynccode/?code=YmRmZTMxOWI1OTg1N2UwYjQ2Yzk0MTRlNjZiZDY0ODNfQ2NOUjJRcUdXcDhDSUJ6RGVDd1lJSFdXUHdUUXJFaTZfVG9rZW46Qm9DRmJEVEdUb2RRWG14VnpzTGM1Y3pjbkdjXzE3OTQxMjY2NjE6MTc5NDEzMDI2MV9WNA&add_watermark=true&scene_type=CCM)

只有已用的内存才在物理内存中分配空间，因此可以容纳巨大的地址空间。在这种情况下，需要一组3对基址和界限寄存器。每个 segment 有自己独立的一套 Base + Bounds。

#### 虚拟内存怎么知道自己属于哪一个段

> 虚拟地址本身会被拆成两部分：**段号（segment number）+ 段内偏移（offset）**。CPU/MMU 通过虚拟地址中的某几位得到段号，再根据这个段号找到对应段的 Base、Bounds 等信息。

假设我们有一个 14 位虚拟地址，并且规定最高 2 位作为段号，那么地址结构可以理解成：

```Plain
| segment |        offset        |
|  2 bit  |        12 bit        |
```

操作系统约定：

- `00` 表示 Code
    
- `01` 表示 Heap
    
- `10` 表示 Stack
    
- `11` 暂时不用
    

那么一个虚拟地址：

```Plain
01 0000 0010 0100
```

MMU 看到前两位是：

```Plain
01
```

就知道：

> 这个地址属于 Heap 段。

剩下的 12 位：

```Plain
0000 0010 0100
```

就是这个地址在 Heap 内部的偏移量。

假设换算出来 offset = 36，那么这个虚拟地址的含义其实不是“物理地址 36”，而是：Heap 段中的第 36 个字节。

然后 MMU 会去找 Heap 对应的段描述信息。

CPU 和操作系统事先约定了虚拟地址的格式，MMU 按这个格式解释虚拟地址。比如规定：$$VA=SegmentNumber+Offset$$

> _**注意但 Stack 往往需要考虑“反向增长”。虚拟地址空间最高地址附近属于 Stack：如果虚拟地址最高两位表示 Stack，那么得到 offset 后，有些实现不会直接用这个 offset，而是先把它转换成一个“负偏移”**_。

#### 分段支持权限控制

要节省内存，有时候在地址空间之间共享（share）某些内存段是有用的。为了支持共享，需要一些额外的硬件支持，这就是保护位（protection bit）。基本为每个段增加了几个位，标识程序是否能够读写该段，或执行其中的代码。通过将代码段标记为只读，同样的代码可以被多个进程共享，而不用担心破坏隔离。

不同 segment 可以设置不同权限。例如：

```YAML
Segment   Read   Write   Execute

Code      yes    no      yes
Heap      yes    yes     no
Stack     yes    yes     no
```

#### 分段的优缺点

分段前整个进程必须连续，分段后：Code → 一块；Heap → 一块；Stack → 一块，它们可以分别放在不同地方。这提高了灵活性，而且避免了虚拟地址空间中那些“大空洞”也必须占物理内存。

但分段也有严重问题：最大问题：

> **外部碎片（External Fragmentation）**

因为 segment 大小不固定。比如物理内存：

```JavaScript
[A 10KB]
[空 5KB]
[B 20KB]
[空 8KB]
[C 10KB]
[空 7KB]
```

总空闲：5 + 8 + 7 = 20KB

现在来了一个：15KB Segment

虽然总空闲：20KB。但没有任何一块连续空间 ≥ 15KB。所以放不下。

### 第十八章 分页：介绍

> 基本概念：**分页**是一种管理内存的方法：把进程看到的虚拟地址空间切成固定大小的块，叫**页（page）**；把物理内存切成同样大小的块，叫**页帧（page frame，也叫页框）**。
> 
> 一定要记住：**页内的位置保持不变**。页号通过页表从 `01` 变成 `111`，而偏移量 `0101` 不变。

**分页**是把进程的虚拟地址空间切成固定大小的**页（page）**，把物理内存切成同样大小的**页框（page frame）**。操作系统可以把一个进程的不同页放到不连续的页框中，程序仍然像在使用一片连续的内存。

**页表**就是记录“虚拟页放在哪个物理页框”的映射表。CPU 访问一个虚拟地址时，会把它拆成两部分：**虚拟页号**和**页内偏移**。虚拟页号用于查页表，找到物理页框号；页内偏移保持不变。

假设页大小为 4 KiB，程序访问虚拟地址 `0x2345`：

- 虚拟页号是 `2`，页内偏移是 `0x345`。
    
- 如果页表记录“虚拟页 2 → 物理页框 7”，最终物理地址就是 `0x7345`。
    

可以把它理解为：_**页表决定去哪一个页框，偏移决定访问页框内的哪个位置**_**。** 实际执行地址转换的是 CPU 中的内存管理单元（MMU）；操作系统负责建立和维护页表。

#### _**页表存在哪：页表主要存放在物理内存中，由操作系统为进程建立和维护。它本身也是数据，也要占用内存页。**_

#### _**页表中有啥：页表里最核心的内容是一个个页表项（PTE）**_

每个页表项描述一个虚拟页：**它映射到哪个物理页框，以及能否访问、如何访问****。**

结合上一张图，虚拟页号是 `01`。用它找到对应的页表项后，里面可能记录着：

|   |   |
|---|---|
|信息|作用|
|物理页框号 111|告诉 CPU 这个虚拟页放在物理内存的哪里|
|存在位|表示当前是否有可用的物理内存映射|
|读、写、执行权限|限制程序能对这个页做什么|
|用户态访问权限|限制用户程序能否访问|
|访问位、脏位|记录这个页是否被访问、是否被修改过|

因此，页表项可以粗略理解为：**`虚拟页 01 → 物理页框 111，附带一组状态和权限`**。页表不存这个页里的具体数据，也不需要存页内偏移；偏移来自原虚拟地址，在转换时保持不变。

### 第十九章 分页：快速地址转换（TLB）

> 使用分页机制来实现虚拟内存不可避免的存在性能问题，分页的性能开销，核心来自一件事：_**CPU 使用的是虚拟地址，访问内存前必须把它翻译成物理地址。**_程序每次读取指令、访问变量，都可能涉及这一步。性能问题主要指的是：**地址翻译、页表维护和缺页处理带来的额外成本**。

我们主要依靠TLB来解决地址转换导致性能问题。

_**TLB（Translation Lookaside Buffer，地址转换后备缓冲区，也叫快表）是 CPU 内用于加速虚拟地址转换的高速缓存**_。它保存近期使用过的虚拟页到物理页帧的映射，以及相应的访问权限等信息。CPU 访问一个虚拟地址时，会先查询 TLB；如果命中，就能快速得到物理地址，省去从内存中查询页表的过程；如果未命中，则需要查询页表，并通常将查到的映射加入 TLB。

**TLB 本身是硬件**：它是 CPU 中用于缓存地址转换结果的一小块高速存储结构，通常属于内存管理单元（MMU）的一部分。

虚拟地址转换为物理地址去访问 和 通过tlb拿到虚拟地址映射难道不是一样的吗？

**两种情况最终都要把虚拟地址转换成物理地址，再访问数据**。TLB 优化的不是“省掉转换”，而是**省掉转换过程中去内存查页表**。

假设 CPU 要读取某个虚拟地址上的数据：

- **TLB 未命中**：先访问内存中的页表，找到物理页帧；再访问内存，读取数据。
    
- **TLB 命中**：直接从 CPU 内的 TLB 取到物理页帧；再访问内存，读取数据。
    

区别就在“映射存放在哪里”：页表在内存中，读取它需要额外的内存访问；TLB 在 CPU 内，查询速度快得多。**真正的数据还是要读取一次，TLB 省掉的是查地址所需的内存访问。**

如果用四级页表举个简化例子：TLB 未命中时，可能要读取 4 个页表项，最后再读取数据；TLB 命中时，可以跳过那 4 次页表查询，直接读取数据。当然，实际耗时还受 CPU 缓存影响，这里只是说明优化发生在哪一步。

#### 上下文切换时的TLB

TLB中包含的虚拟到物理的地址映射只对当前进程有效，对其他进程是没有意义的。所以在发生进程切换时，硬件或操作系统（或二者）必须注意确保即将运行的进程不要误读了之前进程的地址映射。

- 较直接的方式是**切换地址空间时清除相关 TLB 记录**，让 B 之后重新查页表。这样能保证正确，但刚切换后会产生更多 TLB 未命中。
    
- 另一种方式是给 TLB 记录附上 **ASID（地址空间标识符）**。查 TLB 时，硬件同时匹配虚拟页号和 ASID。这样 A、B 的映射可以同时留在 TLB 中；切回 A 时，之前的映射还有机会继续命中。现代处理器的具体实现和名称会有所不同。
